# TEST_PLAN — Lodev Raycasting

## Pre-code toolchain check (must happen first, no exceptions)

Before any code is written or any "tested" claim is made:

1. Confirm a working C++ compiler on the machine that
   will build and run the program (compiler name and
   version recorded).
2. Confirm a display backend on that machine (window /
   screen output for a 640x480 buffer, plus keyboard
   input), and record the choice in DESIGN.
3. If either check fails, the code phase stops and
   reports the blocker; it does not substitute a
   different language silently, and it does not claim
   tests passed without a running program.

No C++ toolchain in this VM is verified by these docs.

## Test philosophy: observable behaviour, not code inspection

A raycaster's correctness is visible on screen. Tests
below are therefore stated as behaviour an observer (or a
headless test harness that renders into a buffer and reads
pixels back) can check, not as "the code contains DDA".
Where a headless harness is used, it must render into the
same buffer the program presents, at 640x480, and read
that buffer — screenshots of a window are not required,
and window-only behaviour that cannot be captured in a
buffer must be tested by a human run and recorded as such.

Tolerances: wall-stripe heights and positions are
integers on screen, so exact pixel-row equality is
expected for the geometric tests below (line height,
draw start/end), except where floating-point rounding
across implementations could shift a boundary by one row;
in that case a tolerance of +/- 1 pixel row is allowed
and must be stated in the test. Colour tests for
textures allow the packed-integer value to match exactly
for a given procedural texture, since the texture is
generated by the program itself — a mismatch means the
texture generation or the mapping changed, not rounding.

## Unit / function tests (DDA and camera)

- **CameraX mapping.** Stripe 0 gives cameraX = -1,
  the centre stripe gives cameraX = 0, the last stripe
  gives cameraX just under +1. Ray direction at the
  centre stripe equals `dir`; at the edges it equals
  `dir - plane` / `dir + plane`.
- **Perpendicularity.** After any rotation, `dir` and
  `plane` remain perpendicular (dot product 0 within
  floating-point tolerance) and keep their lengths.
  A test that rotates by 90 degrees four times must
  return `dir` and `plane` to their starting values
  within tolerance.
- **FOV.** With `dir` and `plane` of equal length, the
  angle between the two outer rays is 90 degrees.
  With a much longer `dir`, the angle narrows; with a
  much shorter `dir`, it widens. (Computed from the ray
  directions, not from a screenshot.)
- **DDA finds the first wall, not a later one.** In a
  known map, a ray aimed at a near wall and then a far
  wall behind it must report the near wall's cell and
  side. A ray down an empty corridor must report the
  corridor's end wall.
- **DDA never skips a cell.** A ray at a shallow angle
  across the grid must visit every grid line it crosses:
  the sequence of (mapX, mapY) steps must change by
  exactly one cell in exactly one axis per step, with
  no diagonal jumps and no missed cells.
- **Zero-component rays.** A ray with rayDirX = 0 or
  rayDirY = 0 must terminate at the correct wall
  (straight ahead / straight sideways) without hanging
  or dividing by zero, under the guard chosen in SPEC
  section 4.
- **Border guarantee.** Every ray from every reachable
  player position in the test maps terminates at a wall
  within a bounded number of DDA steps (the map is
  24x24, so a generous bound such as 100 steps is safe);
  no ray escapes the grid.

## Rendering behaviour tests (untextured)

- **Wall height vs distance.** In a straight corridor,
  a wall twice as far away draws half as tall:
  `lineHeight` is inversely proportional to
  `perpWallDist` (checked at two known distances, e.g.
  a wall 1 unit away vs 2 units away, same orientation).
- **No fisheye.** Facing a straight wall head-on, every
  stripe's wall top and bottom rows are the same across
  the whole screen (within +/- 1 row). The same wall
  viewed at an angle draws taller in the middle than
  at the edges in the correct direction (nearer edge
  taller), not rounded.
- **Vertical centring and capping.** A very close wall
  (lineHeight > screenHeight) is capped to rows
  0..479 with no out-of-bounds draw. A far wall draws
  a short stripe centred on row 240.
- **Side darkening.** For the same wall colour, a
  y-side stripe is darker than an x-side stripe of the
  same wall (checked as a pixel-value comparison, not
  by eye).
- **Map fidelity.** In the untextured test map, standing
  in a known cell facing a known direction produces the
  expected wall pattern: e.g. the inner room's walls
  appear where the map says they are, and pillars
  appear as narrower stripes than full walls at the
  same distance.

## Rendering behaviour tests (textured)

- **Texture selection.** Walls with different map
  numbers draw different textures (different pixel
  patterns in the same stripe position), and the same
  number always draws the same texture.
- **wallX -> texX mapping.** Moving sideways along a
  wall (or, equivalently, shifting the player parallel
  to it) shifts the texture pattern along the stripe
  in the correct direction, and the pattern wraps
  (repeats) at the wall's edge rather than smearing
  or stopping.
- **Vertical texture stepping.** A wall stripe's
  texture rows run top to bottom in order, and a
  taller stripe (closer wall) shows more texture rows
  stretched over more screen rows than a shorter
  stripe of the same wall — i.e. the step
  (texHeight / lineHeight) is applied, not a fixed
  texel per screen row.
- **Affine-mapping limit, documented not hidden.**
  The test records that texture mapping is affine and
  correct for vertical walls; no test claims
  perspective-correct texturing for a slanted surface,
  because this build has none.
- **Y-side darkening on packed colours.** A y-side
  textured stripe's packed RGB values equal the
  x-side values halved per channel, with no channel
  bleed (checked by unpacking R, G, B and comparing,
  not by eye).

## Movement and interaction tests

- **Frame-time independence.** Doubling the simulated
  frame time (e.g. by running the movement update with
  frameTime 0.032 instead of 0.016) doubles the distance
  moved and the angle rotated, for the same input.
- **Point collision.** Attempting to walk into a wall
  cell leaves the player position unchanged (the move
  is rejected); walking in open space moves the player
  by the expected amount. Corner behaviour (moving
  diagonally into a corner) is recorded as tested with
  the axis-separation choice made in DESIGN, not left
  ambiguous.
- **Rotation.** Rotating left then right by the same
  angle returns the view to the starting direction
  (within tolerance), and the wall pattern on screen
  matches the starting pattern.
- **FPS counter.** With a simulated steady frame time,
  the displayed FPS equals 1 / frameTime (within
  rounding). With frameTime = 0, the program does not
  crash on division by zero.

## Integration test (scripted, real program)

- Build the program (after the toolchain check passes).
- Run it headlessly if the backend allows it (render
  into a buffer and dump frames), or run it
  interactively and record the run: at 640x480, the
  program starts, shows walls, moves and rotates on
  input, does not walk through walls, and quits cleanly
  on the quit key.
- Run the untextured build and the textured build
  separately; each must pass its own rendering tests
  above. A pass for one is not a pass for the other.
- No test may claim floors, ceilings, sprites, stairs,
  or height differences, because this build has none.

## Before any push

- All unit, rendering, movement, and integration tests
  above pass, on the verified toolchain.
- A code review against SPEC: every section's
  behaviour present, no out-of-scope feature claimed,
  no tutorial code copied verbatim (implementation is
  ours, following the tutorial's explanation).
- The display backend and toolchain are recorded in
  DESIGN, so a later reader can reproduce the run.
